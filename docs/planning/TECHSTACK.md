## 1. 기술 의사결정 요약

**Next.js(App Router) + React + TypeScript + Tailwind CSS + IndexedDB(Dexie) + Vitest + React Testing Library + Playwright**의 단일 웹 프로젝트를 채택한다.

- **별도 백엔드 서버 없음:** 계정, 결제, 서버 동기화, 외부 API 연동이 MVP의 필수 기능이 아니다.
- **로컬 우선:** 운동 설정과 수행 기록은 사용자의 브라우저 IndexedDB에 저장한다.
- **계산 로직 분리:** TM·중량 스케일링·FST-7 증량은 React에 의존하지 않는 순수 TypeScript 모듈로 구현한다.
- **운동 중 안정성:** 세트 입력은 즉시 저장하고, 타이머는 경과 시간 기반으로 계산한다.
- **비용 최소화:** 정적 배포가 가능하도록 설계하며 호스팅 무료 제공량·정책은 배포 시점에 확인한다.

### 기술 스택

| 영역 | 선택 | 선정 이유 |
|---|---|---|
| 애플리케이션 | Next.js App Router | 라우팅, 화면 구성, 향후 기능 확장 용이 |

| 계산 엔진 | 순수 TypeScript | 계산의 결정성, 단위 테스트, UI 독립성 |

| 상태 관리 | React state/context 중심 | 소규모 MVP에서 불필요한 전역 상태 도입 회피 |

## 2. 프로젝트 범위와 불변 규칙

### 2.1 기본 주간 일정

| 요일 | T1 | T2 | T3(FST-7) |
|---|---|---|---|
| 월 | 벤치프레스 | OHP | 케이블 플라이 |
| 화 | 데드리프트 | 프론트 스쿼트 | 레그 컬 |
| 수 | 휴식 | — | — |
| 목 | 스쿼트 | 스모 데드리프트 | 레그 익스텐션 |
| 금 | OHP | 인클라인 벤치프레스 | 덤벨 사이드 레터럴 레이즈 |
| 토 | 바벨 로우 | 슈러그 | 랫풀다운 |
| 일 | 휴식 | — | — |

- **T1:** 기본 종목 고정. T1·T2의 사용자가 입력한 1RM을 기준으로 `initialTM = 1RM × 0.90` 계산, 이후 `currentTM`은 별도 관리. 바벨 로우는 일반 5/3/1 벤치형 T1 템플릿 재사용.
- **T2:** 종목 교체 가능. 서로 다른 종목은 독립적인 1RM·TM을 가지며, 새 종목 선택 시 해당 currentTM 및 운동 유형별 T2 템플릿을 이용해 전체 목표 세트를 재계산. T1과 같은 exerciseId는 공통 프로필·currentTM을 참조.
- **T3:** 종목 교체 가능. **12회 × 7세트 고정**. 초기 작업 중량 직접 입력; 7세트 전부 목표를 달성한 경우 다음 세션에 운동별 설정 단위만큼 증량.
- **중량 단위:** 종목별로 설정하며, 덤벨은 한 손 중량인지 명확히 표기.
- **휴식 타이머:** T1 180초 / T2 120초 / T3 30초 기본값. 사용자 조절 가능.
- **기록:** 회원가입 없이 기기·브라우저별 로컬 저장.

**중요:** 원본 nSuns 요일별 T1 세트표, 바벨 로우가 재사용할 벤치형 T1 템플릿의 세트 데이터, T2 운동 유형별 세트 비율, AMRAP 증량 고정값은 **아직 검증·확정되지 않았다**. 개발자가 비율을 추측해 넣지 않도록 템플릿 승인 전 해당 계산을 활성화하지 않는다.

## 3. 권장 아키텍처

```text
사용자 모바일 브라우저
         │
         ▼
Next.js / React UI
  ├── 루틴 설정 / 운동 변경
  ├── 운동 수행 / 세트 기록
  ├── 휴식 타이머
  └── 진행 상태·기록 조회
         │
         ├── 순수 TS 계산 엔진 (TM, T1/T2 세트, FST-7 진행)
         │
         └── 저장 계층 (Dexie / IndexedDB)
                    ├── 운동별 기준 중량
                    ├── 사용자 변경 루틴
                    ├── 운동 세션·세트 기록
                    └── 타이머 환경설정
```

UI는 계산·저장을 직접 수행하지 않고 각각의 서비스 함수를 호출한다. 계산 모듈은 브라우저 API, React hook, 데이터베이스 접근에 의존하지 않는다.

### 정적 배포 방침

- MVP 페이지는 브라우저에서 동작하는 클라이언트 중심 화면으로 구성한다.
- 서버 전용 기능(API Routes, 서버 액션, 동적 SSR)을 기본 설계에 도입하지 않는다.
- Next.js `output: 'export'`를 사용할 수 있는지 사용 중인 기능과 함께 검증한다.
- 정적 자산을 지원하는 무료 호스팅에 배포할 수 있도록 한다. 무료 요금제·트래픽 조건은 배포 전에 최신 문서를 확인한다.

## 5. 주요 기술 설계

### 5.1 자동 중량 스케일링

1. 운동 ID로 저장된 운동 프로필(T1/T2: 1RM·currentTM, T3: 작업 중량)을 조회한다. 같은 exerciseId는 T1·T2가 하나의 프로필을 공유한다.
2. 신규 운동이라면 사용자에게 기준 중량을 입력받는다. **다른 운동의 중량을 임의로 전용하지 않는다.**
3. T1/T2 신규 입력 시 `initialTM = 1RM × 0.90`을 계산하고 `currentTM`의 초기값으로 사용한다. 이후 계산은 `currentTM`을 사용한다.
4. 승인된 해당 티어 템플릿(T2는 운동 유형별)의 세트별 반복수·TM 비율을 적용한다.
5. 운동별 설정된 증량 단위에 맞춰 **최종 표시 중량만** 반올림한다. 가장 가까운 단위를 고르고 정확한 중간값은 높은 중량을 선택하며, 부동소수점 오차를 고려한다.
6. 목표 중량, 수동 수정 중량, 실제 완료 중량은 서로 구분한다.
7. 종목을 교체해도 과거 세션 기록은 변경하거나 삭제하지 않는다.

T1 바벨 로우는 **일반 5/3/1 벤치형 T1 템플릿을 재사용**하되 원본 nSuns에 있는 운동인 것처럼 표현하지 않는다. 벤치형 템플릿의 정확한 식별자와 세트 데이터는 원본 검증 후 등록한다.

**TM 상태와 스냅샷:** 운동 프로필은 `initialTM`(1RM 파생값)과 `currentTM`(독립 저장값)을 구분한다. currentTM 변경은 TM 변경 이력으로 남기고, 세션 시작 시 적용 TM·템플릿 버전·증가 단위는 SessionExercise에, 목표 중량·반복은 SetRecord에 스냅샷으로 저장한다. 자동 증량은 `(세션, 운동, 티어)` 기준으로 한 번만 적용한다. 계산 엔진은 새 값을 반환만 하고, 저장은 저장 계층(Dexie repository)이 담당한다.

### 5.2 T3 자동 증량

- 모든 세트의 목표 반복은 12회, 총 7세트다.
- 사용자 작업 중량을 첫 목표 중량으로 사용한다.
- **7세트 모두 12회 이상 수행하고 실제 중량이 해당 세션의 목표 중량 이상이면** 다음 세션의 작업 중량을 한 단위 올린다.
- 미완료 또는 한 세트라도 목표 미달이면 기본적으로 중량을 유지한다.
- 완료된 세트·세션 기록은 수정할 수 없으므로 기록 수정에 따른 다음 중량 재평가는 발생하지 않는다. 완료된 세션의 실제 기록은 자동 변경하지 않는다.

### 5.3 휴식 타이머

- 세트 완료 체크의 **저장 성공 후**, 같은 운동에 미완료 세트가 남아 있으면 해당 티어의 기본 휴식 시간으로 자동 시작한다. 저장 실패 시 시작하지 않는다.
- 시작/종료 예정 시각을 기반으로 남은 시간을 계산한다. `setInterval`은 표시 갱신 용도로만 사용한다.
- 일시정지·재개, ±15초, 건너뛰기를 지원한다.
- 백그라운드에서 타이머 실행 정밀도를 보장하지 않는다. 복귀 시 경과 시간에 따라 화면을 재계산한다.
- 모바일 웹에서 소리·진동·브라우저 종료 알림은 지원 여부와 사용자 동작 조건에 제한이 있으므로, 지원 가능한 환경에서만 제공한다.
- 마지막 세트의 휴식 여부 및 다음 티어 전환 타이머는 UI 설계에서 명확히 정의한다.

### 5.4 로컬 저장

Dexie를 이용해 IndexedDB에 다음 데이터를 보관한다.

| 저장 항목 | 예시 |
|---|---|
| 운동 정의 | 종목 ID, 장비, 중량 표시 방식, 증량 단위 |
| 운동별 프로필 | exerciseId당 1개(T1·T2 공통): 1RM, initialTM, currentTM, T3 작업 중량, 마지막 수정 시각 |
| TM 변경 이력 | 변경 전·후 TM, 사유, 근거 세션·티어, 규칙 ID·버전, 적용 시각 |
| 사용자 루틴 | 요일별 T2/T3 변경 내용 |
| 수행 세션 (WorkoutSession) | 하루 운동 단위: 시작·종료 시각, 상태, 실제 수행 날짜 |
| 세션 운동 (SessionExercise) | 세션 안의 운동 실행 단위: sessionExerciseId(유일), sessionId, exerciseId, tier, 진행 상태, 적용 TM·작업 중량·템플릿 버전·증가 단위 스냅샷, resetCount, lastResetAt |
| 세트 기록 (SetRecord) | sessionExerciseId 소속: 세트 번호, 목표/실제 중량, 목표/실제 반복, 완료 상태·완료 시각 |
| 환경설정 | 티어별 휴식 시간, 표시 단위 |

- 세트 완료는 체크박스 체크 시 저장하며, **저장 성공을 완료 상태의 기준**으로 한다. 저장 실패를 UI에 표시한다.
- 현재 세트 위치(`currentSetIndex`)는 기본적으로 저장하지 않고, 운동의 SetRecord 중 `completed = false`인 첫 세트로 계산한다.
- 데이터 마이그레이션을 위해 DB 스키마 버전을 관리한다.
- IndexedDB는 **기기·브라우저별 저장소**이며 자동 클라우드 동기화가 없다.
- 사생활 보호 및 기록 유지를 위해 개인정보 수집을 최소화한다.
- 브라우저 캐시·사이트 데이터 삭제, 시크릿 모드, 저장소 제한 등으로 데이터가 손실될 수 있으므로 안내한다.
- JSON 내보내기·가져오기는 장기 이용을 위해 강하게 권장한다. MVP 필수 포함 여부는 기능 명세에서 별도 결정한다.

#### 세트 완료 저장 (저장 성공 기준 상태 확정)

- **비관적 갱신:** UI는 `completeSet()`의 Dexie 쓰기가 성공한 뒤에만 체크 완료·잠금을 표시한다. 저장 대기 중에는 해당 세트를 "저장 중"으로 표시하고 입력·체크를 막는다.
- **트랜잭션:** `completeSet()`은 Dexie `rw` 트랜잭션 하나에서 다음을 처리한다.
  1. 하루 세션 상태 재확인 (IN_PROGRESS)
  2. 대상 SetRecord를 다시 읽어 아직 미완료인지 확인 (이미 완료면 거부 — 중복 체크 방지)
  3. 검증된 `actualWeight`·`actualReps`와 `completed = true`, `completedAt`을 함께 기록
- **실패 처리:** 트랜잭션이 실패하면 세트는 미완료로 남는다. UI는 체크를 되돌리고 입력값을 보존하며 재시도를 제공한다. 휴식 타이머는 시작하지 않는다.
- **검증 위치:** 입력값 검증은 순수 함수(`validateSetCompletion()`)로 수행하고, 저장 계층은 검증을 통과한 값만 받는다. 가져온 데이터 검증용 Zod 스키마와 같은 규칙을 공유할 수 있다.

#### 세트 완료 잠금과 운동별 리셋

- **관계:** WorkoutSession 1 : N SessionExercise 1 : N SetRecord. 세트는 `sessionExerciseId`로 소속 운동을 찾으므로 세트 테이블에 `sessionExerciseId` 인덱스가 필요하다. 같은 `exerciseId`가 여러 세션에 있으므로 리셋 대상은 `exerciseId`가 아니라 `sessionExerciseId`로 식별한다.
- **세트 잠금:** 저장 계층(repository)은 일반 세트 수정 요청에서 `completed = true`인 세트의 변경을 거부한다. UI 비활성화만으로 잠금을 보장하지 않는다. 승인된 운동 리셋은 별도 작업 `resetSessionExercise()`로만 수행한다.
- **리셋 원자성:** `resetSessionExercise(sessionExerciseId)`는 Dexie `rw` 트랜잭션 하나에서 다음을 처리하고, 하나라도 실패하면 전체를 롤백한다.
  1. 하루 세션 상태 재확인 (IN_PROGRESS·PAUSED만 허용, 트랜잭션 **안에서** 다시 읽음)
  2. 대상 SessionExercise 식별 (요청한 세션에 소속되었는지 확인)
  3. 대상 운동의 SetRecord만 실제 중량·반복·완료 상태·완료 시각 초기화
  4. 대상 운동의 진행 상태를 저장하는 경우 NOT_STARTED로 재설정 (현재 세트는 계산값이므로 자동으로 첫 세트가 됨)
  5. 대상 운동의 `resetCount`·`lastResetAt` 갱신
- **트랜잭션 범위:** 쓰기 대상은 대상 SessionExercise 1건과 그 SetRecord뿐이다. WorkoutSession은 상태 확인을 위해 읽기만 하며 상태를 바꾸지 않는다. 다른 SessionExercise·SetRecord는 변경하지 않는다.
- **스냅샷 보존:** 리셋은 세트의 실제값·완료 상태만 초기화하고, SessionExercise의 TM·작업 중량·템플릿 버전·증가 단위 스냅샷과 세트의 목표 중량·반복은 수정하지 않는다.
- **증량과의 분리:** 리셋 트랜잭션은 운동 프로필·TM 변경 이력·증량 이벤트 테이블을 건드리지 않는다. 증량 멱등성은 `(세션, 운동, 티어)` 키로 계속 보장한다.
- **완료·중도 종료 세션:** COMPLETED(U-14)·ABANDONED(U-15) 세션의 운동 리셋은 정책이 확정될 때까지 저장 계층에서 거부한다.
- **사용자 확인과 저장의 분리:** 확인 모달은 UI 책임이며, 저장 계층은 확인 이후에 호출된다.

## 6. 테스트 전략

| 테스트 층위 | 도구 | 핵심 시나리오 |
|---|---|---|
| 단위 | Vitest | `initialTM=1RM×0.9`, 반올림(중간값 상향), T1/T2 세트 생성, 동일 exerciseId TM 공유, 증량 중복 방지, FST-7 성공 판정 |
| 컴포넌트 | React Testing Library | 운동 변경, 신규 기준 중량 요청, 세트 체크박스(저장 중·성공·실패 표시, 해제 불가), 세트 완료 전 수정·완료 후 잠금, 운동 리셋 확인·취소, 타이머 조작 |
| 통합 | Vitest + IndexedDB 테스트 환경 | 저장·복원·마이그레이션, 과거 기록 불변성, 세트 완료 저장 실패 시 미완료 유지, 중복 체크 거부, 완료 세트 잠금, 운동 리셋 원자성·롤백, 다른 운동 기록 불변, 완료·중도 종료 세션의 운동 리셋 거부 |
| E2E | Playwright | 모바일 폭에서 초기 설정 → 운동 변경 → 7세트 완료 → 새로고침 복원 |

**필수 테스트 원칙**

- 실제 nSuns 템플릿 검증 전 가상의 비율을 운영 계산 로직에 넣지 않는다.
- 동일 입력·동일 템플릿이면 동일 결과를 반환해야 한다.
- 0, 음수, 비정상 입력, 미입력, 소수점 단위·반올림 경계값을 테스트한다.
- 새로운 운동을 선택했을 때 기존 운동의 중량을 잘못 복사하지 않아야 한다.
- T3 한 세트라도 미달할 경우 증량하지 않아야 한다.
- 운동 변경 후 과거 기록이 남아 있어야 한다.
- 모바일 타이머의 백그라운드 복귀와 새로고침 이후 표시를 검증한다.

## 7. 비용·성능·접근성·보안

- **비용:** 핵심 기능에 서버 DB, 유료 API, 유료 AI API를 쓰지 않는다. 호스팅 무료 정책은 별도 확인한다.
- **성능:** 계산은 사용자의 입력 변경 직후 브라우저에서 수행한다. UI 업데이트와 DB 저장은 분리하여 지연을 최소화한다.
- **접근성:** 모바일 최소 폭을 고려하고, 충분한 터치 영역의 세트 완료 체크박스·명확한 라벨·키보드 접근·충분한 대비를 제공한다.
- **데이터 안전:** 기록을 임의로 덮어쓰지 않고 저장 실패를 안내한다. 백업 기능 없이 기기를 바꾸면 기록을 옮길 수 없음을 표시한다.
- **보안:** 사용자 입력과 가져온 JSON을 검증한다. 외부 비밀키를 클라이언트에 두지 않는다(현재는 비밀키 불필요).
- **운동 안전:** 권장 중량은 기록 기반 계산치이지 부상 위험 평가나 의료적 권고가 아니다. 사용자 수정 기능을 유지한다.

## 10. 최종 결정

**nSuns Hybrid MVP는 프론트엔드·백엔드 분리 없이 하나의 Next.js 프로젝트로 구현한다.**

그러나 아키텍처 내부에서는 **UI / 운동 도메인 계산 / IndexedDB 저장 계층을 명확하게 분리**한다. 이것이 운동별 자동 중량 스케일링의 정확성을 검증하고 향후 클라우드 기능을 추가할 때의 변경 비용을 낮추는 가장 중요한 기술 원칙이다.

**문서 상태:** TECHSTACK v1.0 작성 완료 / 계산 템플릿 검증 및 UI 설계 대기.
